# Lumos 22단계 새 환경 재현·버전 기록

> **기록 상태: 초안 / 재현 준비 중.** 아래에는 이번 작업에서 코드·설정 파일로 확인 가능한 프로젝트 메타데이터와, 향후 별도의 새 환경(격리 폴더)에서 검증해야 할 재현 항목 및 주의사항을 구분해 기술했습니다.
>
> 22단계 평가 기준상 별도의 독립 폴더(Clean Room)에서 실제 Git 체크아웃, 새 환경 실행, 브라우저 화면 관찰, 종료 및 재실행을 직접 수행하기 전까지는 모든 런타임 결과 및 외부 연동 항목을 **미확인**으로 유지하여 문서 전반의 일관성을 유지합니다. AI의 코드 검토는 새 환경에서 실행했다는 증거가 아니며, `demo`/모의 자료, 연결 없음, 실제 시스템 연결을 엄격히 분리합니다.

## 1. 제출할 원문과 버전

| 항목 | 기록 |
|---|---|
| Agent 표시 이름 | Lumos (포털·학생 안내용. 시작 틀의 파일·폴더명과 기본 앱 제목은 자동 변경되지 않음) |
| 프로젝트 패키지 버전 | `on-client/package.json`: `0.2.11` (파일에서 확인) |
| 검증 릴리스 표기 | 검증 중 — `v1.0` 아님 |
| 저장소 주소 | 미기록 — 본인 PC·과제 화면에서 확인하고 자격 정보는 제거 (`HaYul0611/Lumos-Agent`) |
| 브랜치 | 미기록 — 본인 PC에서 확인 (기본 브랜치 `master` / `main`) |
| 최종 제출 커밋(40자리) | 미기록 — 본인 PC의 최종 커밋에서 확인 |
| Git 최상위 폴더 | 시작 틀 안내 기준으로 `on-client`의 상위 프로젝트 폴더 (`Lumos-Agent`) |
| 재현 폴더 | 미기록 — 원래 프로젝트 바깥의 별도 격리 폴더 |
| 운영체제 / Node.js / PowerShell | 미확인 — 재현을 수행할 새 PC/환경에서 직접 측정하여 기록 (`package.json` 권장: Node.js 24.19.0) |
| 확인자 / 확인 시각 / 시간대 | 미기록 — 새 환경 재현 시점에 학생 본인이 기입 |

**커밋 식별 주의:** 커밋에는 그 커밋 자체의 40자리 해시를 내용으로 넣을 수 없습니다. 해시를 문서에 넣으면 문서가 바뀌어 새 커밋이 되기 때문입니다. 최종 커밋 해시는 과제 화면의 저장소·커밋 입력과 별도 제출 기록에서 확인·기록하고, 이 문서에는 새 환경에서 실제로 검사한 커밋을 재현 시점에 기록합니다. 문서 내용을 바꾸면 새 커밋이므로 변경된 커밋을 다시 식별하고 재현해야 합니다. 제출 방식이 이 구분과 다르면 해당 단계 화면의 지침을 우선 확인합니다.

Git 상태를 이 도구로 확인할 수 없어 저장소 URL, 브랜치, 변경 파일, 원격 저장소 등록 여부, 커밋은 미확인입니다. 새 문서와 이번 단계 코드를 같은 커밋으로 만들기 전에 본인 PC에서 `git status --short`로 준비 중인 작업을 먼저 살펴보고 기존 작업을 보존하세요. 커밋 해시나 변경 파일을 추측하지 마세요.

## 2. 같은 커밋의 별도 폴더 재현

1. 원래 작업 폴더와 Git 기록을 그대로 보존합니다. 재현은 원래 폴더와 분리된 새 폴더에서만 합니다. 원래 폴더를 초기화하거나 새 폴더로 바꾸지 않습니다.
2. 본인 PC에서 Git 최상위 경로, 저장소 주소, 브랜치와 제출 대상으로 삼을 40자리 커밋을 확인합니다. 공개 저장소는 해당 저장소에서 새 폴더로 받습니다. 비공개 저장소는 과제 화면의 「비공개 저장소 원문 준비 방법」을 따릅니다. 저장소 공개 전환은 하지 않습니다.
3. 새 폴더에서 실제 체크아웃한 커밋이 제출할 커밋과 같은지 확인합니다. 다른 커밋이면 그 실행 결과를 최종 커밋의 재현이라고 기록하지 않습니다. 자격 정보가 포함된 URL이나 토큰은 명령·문서·대화에 넣지 않습니다.
4. 인증·설정 파일을 기존 폴더에서 무작정 복사하지 않습니다. 별도 설정이 필요하면 담당자가 승인한 절차를 따르고 비밀값은 프로젝트와 Git 바깥에 둡니다.
5. [학생용 실행 설명서](STUDENT_RUNBOOK.md) 2~5절과 [시작·실행 안내](STUDENT_LAUNCH_GUIDE.md)에 따라 런타임 확인, 실행, 브라우저 확인, 종료와 같은 커밋 재실행을 차례로 수행합니다. 프로젝트의 `package.json`에는 외부 npm 의존성 선언이 없습니다. 파일 검색에서 `package-lock.json`을 찾지 못했으므로, 이 상태만으로 `npm install`이 필요하다고 추정하지 않습니다.
6. 화면에서 직접 관찰한 결과와 시각을 기록합니다. 실행 도구의 서버 응답 안내만으로 AI·SDP/XDR 연결이나 단계 통과를 주장하지 않습니다. `demo`, 연결 없음, 실제 연결을 구분합니다.
7. 문제를 고쳐 새 커밋을 만들었다면 이전 커밋과 새 커밋의 결과를 한 버전의 성공으로 합치지 않습니다. 새 최종 커밋을 식별해 별도 재현 기록을 남깁니다.

## 3. 13~21단계 결과와 증거

이번 단계에서 확인한 것은 프로젝트 파일·문서의 일부 메타데이터와 기존 문서 내용입니다. 학생 코드 전체의 각 함수 입력 계약을 독립적으로 재검증하거나 새 환경 브라우저에서 단계별 동작을 독립 검증하지 않았습니다. 아래 함수명은 기존 실행 설명서의 범위 목록이며, 코드상 존재·동작·평가 통과를 이 표만으로 입증하지 않습니다. 각 단계 결과는 같은 최종 커밋의 새 폴더에서 직접 확인한 뒤 기록합니다.

| 단계 | 점검 대상 | 실제 새 환경 결과 | 시각·증거 / 미확인 이유 |
|---|---|---|---|
| 13 | 로그인·기기·세션 (`renderIdentity`) | 미확인 — 새 환경 화면 및 본인 데이터 재조회 미실행 | 실행 증거 없음 |
| 14 | 업무 앱 접근 결과 (`renderDecision`) | 미확인 — 계정의 실제 판정·이유·시각 미확인 | 화면/응답 증거 없음 |
| 15 | 접속 기록·XDR (`renderEvents`) | 미확인 — 목록·필터·상세 미확인 | 화면 증거 없음 |
| 16 | 상태·알림·진단 (`renderStatus`) | 미확인 — 빈 상태·오류·수동 재시도·복사 미확인 | 화면/네트워크 증거 없음 |
| 17 | AI 연결 (`renderAiConnection`) | 미확인 — 판정과 앱의 AI 연결은 별개 | 계정·네트워크 결과 없음 |
| 18 | 근거 연결 설명 (`renderExplanation`) | 미확인 — 기록별 실제 AI 설명과 근거 일치 미확인 | 유료 요청 및 실제 화면 확인 안 함 |
| 19 | 보안 조치 (`renderAction`) | 실제 조치 집행 연결은 미완료·미확인 | 기본 실행은 조치 미지원이며 실제 조치 미실행 |
| 20 | 설치 패키지·OSV (`renderVulnerabilities`) | 미확인 — 잠금 파일·정확한 설치 버전·OSV 결과 미대조 | `package-lock.json`을 찾지 못했고 조회 실행 안 함 |
| 21 | 실행 설명서·구성도 | 문서 파일 존재는 확인, 새 환경 재현과 공식 판정은 미확인 | 실행·평가 증거 없음 |

실제 확인이 끝나면 `미확인`을 지우기만 하지 말고 관찰 결과, 날짜·시간대, 확인한 커밋, 비밀값을 가린 근거의 위치를 적습니다. 예제 결과는 `demo`, 연결이 없는 결과는 `연결 없음`, 실제 시스템에서 확인한 결과는 실제 연결로 분명히 구분합니다. 실패, 빈 결과, 조회하지 않음은 성공으로 바꾸어 적지 않습니다.

## 4. 데이터 보존·백업·복원 계획과 제한

### 1. 조치 데이터베이스 저장 위치 (`databasePath`) 분석 및 상태
- **소스 코드상 정의**: 조치 모듈(`src/actions/README.md`, `src/actions/action-startup-config.mjs`, `src/actions/store.mjs`)에 따르면 조치 데이터 저장은 자동 생성 경로가 아니며, 서버 시작 시 호스트 CLI 인자(`--alekov-actions --alekov-actions-config <절대경로>`)로 주어지는 `databasePath`를 통해서만 지정됩니다.
- **경로 계약 조건**: `databasePath`는 임의의 상대 경로나 존재하지 않는 경로를 허용하지 않으며, **호스트 머신에 이미 존재하는 단일 일반 SQLite 파일(단일 링크, symlink 아님, 16바이트 SQLite format 3 헤더 포함)의 정규화된 절대 경로**여야 합니다.
- **현재 작업 공간 내 실제 `databasePath` 상태**: **미확인 (현재 지정된 파일 없음)**.
  - 기본 실행 스크립트(`tools/start-alekov.ps1`) 및 기본 실행(`node src/server.mjs`)은 `--alekov-actions` 인자를 넘기지 않는 기본 비활성화(`ACTION_UNSUPPORTED`) 상태입니다.
  - 현재 저장소(`on-client/`) 내부에는 사전에 생성된 기본 `.db`나 `.sqlite` 파일이 존재하지 않으며, 호스트가 외부 파일 시스템의 절대 경로로 제공하도록 설계되어 있습니다.
  - 따라서 고정된 특정 내부 경로나 임의의 가상 경로(`.\data\*.db` 등)를 실제 DB 경로라고 단정할 수 없으며, 운영자/호스트가 제공하는 실제 설정 파일 내의 `databasePath` 절대 경로를 확인하기 전까지는 **경로 미확인** 상태로 기록합니다.

### 2. 사용자 데이터 백업 절차 (실제 `databasePath` 기준)
1. **사전 준비 및 경로 확인**: 호스트가 전달한 `--alekov-actions-config` 설정 파일(JSON)을 열어 기재된 `databasePath`의 실제 정규화된 절대 파일 경로(예: `$DB_PATH`)를 식별합니다. (설정된 DB 파일이 없으면 백업 대상 없음)
2. **앱 서버 정상 종료**: 쓰기 트랜잭션 도중 파일 복사로 인한 데이터 손상(Corruption)을 방지하기 위해, 실행 중인 PowerShell 창에서 `Ctrl+C`를 입력하여 로컬 Node.js 서버 프로세스를 완전히 종료합니다.
3. **안전한 외부 백업 디렉터리 생성**: 프로젝트 및 Git 형상 관리 범위 바깥의 별도 안전한 위치(예: `C:\Users\User\Lumos-Agent-Backups\<날짜_시간>\`)를 생성합니다.
4. **절대 경로 파일 복사**: 식별된 실제 `$DB_PATH` 파일과 설정 파일을 백업 디렉터리로 복사합니다.
   ```powershell
   # 실제 databasePath 절대 경로가 'C:\SecureData\alekov-actions.db'로 확인된 경우의 예시
   # (서버 프로세스가 완전히 종료된 상태에서 수행)
   $actualDbPath = "C:\SecureData\alekov-actions.db"  # 실제 확인된 databasePath 절대 경로
   $backupDir = "C:\Users\User\Lumos-Agent-Backups\$(Get-Date -Format 'yyyyMMdd_HHmmss')"
   New-Item -ItemType Directory -Path $backupDir -Force
   Copy-Item -LiteralPath $actualDbPath -Destination $backupDir
   ```

### 3. 사용자 데이터 복원 절차 (실제 `databasePath` 기준)
1. **서버 프로세스 중단 확인**: 복원 대상 앱 서버가 실행 중이지 않은지 확인하고, 실행 중이면 먼저 정상 종료합니다.
2. **손상된 원본 파일 격리**: 문제가 발생한 원본 SQLite 파일이 남아 있는 경우 다른 이름(예: `$actualDbPath.corrupted`)으로 백업/격리합니다.
3. **백업본 원본 절대 경로로 복원 덮어쓰기**: 백업 디렉터리에 보관된 SQLite 파일을 원래의 정규화된 절대 경로(`$actualDbPath`) 위치로 복사(덮어쓰기)합니다.
   ```powershell
   Copy-Item -LiteralPath "$backupDir\alekov-actions.db" -Destination $actualDbPath -Force
   ```
4. **무결성 및 권한 검증**: 복원된 파일이 단일 일반 파일이며 링크(symlink)가 아니고, 올바른 SQLite 헤더(16 bytes: `SQLite format 3\0`)를 유지하고 있는지 확인합니다.
5. **서버 재실행 및 확인**: 서버를 시작하고 브라우저에서 조치 이력 및 상태가 정상적으로 인식되는지 확인합니다.

### 4. 복원 시험 결과 및 한계
- **현재 환경에서의 시험 상태**: **미확인 (실제 호스트 DB 미지정)**.
  - 현재 저장소 환경에서는 호스트의 실제 조치 DB 경로(`databasePath`)가 제공되지 않은 기본 실행 상태이므로, 실제 운영 DB 파일에 대한 백업 및 복원 시험을 직접 수행하지 못했습니다.
  - 별도 모의 시험 환경에서 격리된 임시 SQLite 파일을 생성하여 프로세스 종료 후 복사·덮어쓰기 시 기저 스키마(`alekov_action_intents`, `state`, `audit`)가 유지되는 것을 기술적으로 검토하였으나, 이를 공식 복원 시험 통과로 과장하지 않습니다.
- **기술적 한계 및 주의사항**:
  - SQLite 특성상 쓰기 작업(`BEGIN IMMEDIATE`) 도중 프로세스가 비정상 종료되거나 전원이 차단되면 커밋되지 않은 트랜잭션은 롤백되어 반영되지 않을 수 있습니다.
  - 네이티브 SQLite 모듈은 busy 대기를 0으로 설정(`PRAGMA busy_timeout=0`)하므로, 다른 프로세스에 의해 파일 잠금이 발생하면 `ACTION_STORE_FAILED`로 즉시 실패 폐쇄되며 자동 재시도하지 않습니다.
  - 로컬 SQLite DB 백업은 로컬 조치 인텐트·감사 기록에 한정되며, 외부 AI 게이트웨이나 원격 SDP 서버의 상태는 포함되지 않습니다.
  - Git clone이나 커밋 원문 묶음은 소스 코드 복구 절차일 뿐이며, 런타임에 사용하는 로컬 SQLite 파일은 Git 관리 대상이 아니므로 별도 절차로만 보존·복원됩니다.

## 5. 버전·지원 범위·미해결 사항

`on-client/package.json`에서 확인한 앱 패키지 버전은 `0.2.11`, Node.js 기준은 `24.19.0`입니다. `tools/start-alekov.ps1`은 Node.js 22~24를 허용하며 24.19.0을 권장합니다. 현재 PC에 설치된 런타임은 확인하지 않았습니다. 저장소·브랜치·최종 커밋과 새 환경 실행 결과를 확인하지 않았으므로 상태는 **검증 중**이며 `v1.0`이나 운영 인증으로 표시하지 않습니다.

미해결·미확인 항목:

- 저장소 URL, 브랜치, 제출 커밋 40자리 및 원본 변경 보존 상태
- 같은 커밋의 별도 폴더 체크아웃, 실행, 브라우저 화면 확인, 종료·재실행
- 실제 AI·SDP/XDR 연결과 13~21단계 화면 결과
- 19단계 실제 조치 원천 집행 연결(미완료); 시험용 표시나 자동 확인은 실집행 증거가 아님
- `package-lock.json`, 실제 설치 패키지 버전, OSV 조회 결과
- 조치 모듈에 사용되는 실제 `databasePath` 절대 경로 및 실제 운영 데이터 백업·복원 시험
- 공식 평가 및 제출 상태

22단계의 AI 원문 검토 또는 제출 접수는 로컬 새 환경 실행 성공, 실제 운영 인증, 실제 조치 연결, 자동 `v1.0` 발급을 뜻하지 않습니다.

## 6. 다음 확인 — 한 번에 하나

**확인 1: 원래 폴더와 Git 기록을 보존하는지 확인합니다.** 먼저 본인 PC에서 프로젝트의 Git 최상위 폴더를 찾고, 그 폴더에서 PowerShell로 아래 읽기 전용 확인을 진행하세요. 현재 작업물은 이 명령들로 수정되지 않습니다.

```powershell
git status --short
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git remote -v
```

변경이 있으면 내용을 확인하고 그대로 보존하세요. 원격 주소 출력에 사용자명이나 자격 정보가 섞일 수 있으므로 결과 전체를 대화에 붙여 넣지 마세요. 저장소 주소를 문서·과제 화면에 적을 때 자격 정보는 제거합니다. 이 확인이 끝난 뒤에만 주소·브랜치·커밋을 확인하고, 과제 화면의 공식 절차에 따라 기존 폴더와 별개인 새 폴더에서 같은 커밋을 재현하세요.

이 AI는 Git·PowerShell·브라우저 명령을 실행하지 않았고, 포털 제출·AI 요청·보안 조치도 하지 않았습니다.
